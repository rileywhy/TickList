## Critical

### C1 — `POST /ticks` is a mass-assignment IDOR: any user can overwrite and steal any other user's tick

`TickController.java:41-44`

```java
@PostMapping({"/ticks", "/tick"})
public Tick createTick(@RequestBody Tick tick, @AuthenticationPrincipal User user) {
    gradeMappingService.applyGradeMapping(tick);
    tick.setUser(user);
    return tickRepository.save(tick);
}
```

The request body binds straight onto the `Tick` **entity** and `id` is never cleared.
`JpaRepository.save()` on a non-null id performs a `merge`, not an `insert`.

Repro: Bob, a legitimately logged-in user, POSTs `{"id": 42, "climbName": "pwned"}` where 42 is
Alice's tick. Spring merges over row 42; `setUser(user)` then reassigns ownership to Bob. Alice's
tick vanishes from her list, and every field Bob didn't send (`notes`, `location`, `stars`,
`pitches`, `climbHeight`, `personalGrade`) is nulled by the merge.

`GET`/`PUT`/`DELETE` are all correctly guarded by `findByIdAndUser`. `POST` is the one unguarded
write path. The frontend never sends `id`, which is exactly why it went unnoticed.

`TickOwnershipIntegrationTest` has 10 tests including "POST ignores a `user` in the body" — but
never "POST with someone else's `id`". The suite reads as complete while leaving the hole open.

**Fix:** `tick.setId(null)` in `createTick`, or bind a `TickRequest` DTO instead of the entity
(preferred — see M4). Add the missing test.

> **RESOLVED 2026-07-27 (`433c5b2`).** `createTick` now rejects a non-null `id` with 400 rather than
> silently nulling it. Rejecting is preferable to sanitising here: it never performs a lookup, so —
> unlike a fix that loads the tick and returns 403/404 — it cannot be used as an existence oracle.
>
> Two corrections to the fix suggested above:
> - **`Tick` has no `setId`**, so `tick.setId(null)` does not compile as written.
> - Adding one would not have been the relevant lever anyway. `id` is bindable **despite** having no
>   setter — Spring Boot's `ObjectMapper` populates the private field directly. The intuition "no
>   setter means not bindable" is false for any entity bound as `@RequestBody`.
>
> Test added: `createTickCannotHijackForeignTickById`. Verified load-bearing by removing the guard —
> the request then returned 200 and the row came back owned by `bob@example.com`, confirming the
> merge-and-steal path was live rather than theoretical.
>
> M4 (request DTOs) still stands. This guard is per-endpoint; the DTO makes the bug unrepresentable.

### C2 — An expired token puts the app in a permanently broken state that never prompts re-login

`SecurityConfig.java:26-42`, `JwtAuthenticationFilter.java:61-63`, and every frontend caller.

`SecurityConfig` configures no `authenticationEntryPoint`, so Spring Security 6 falls back to
`Http403ForbiddenEntryPoint`. `JwtAuthenticationFilter` catches `JwtException`, clears the context,
and calls `filterChain.doFilter` anyway — so an expired token reaches `anyRequest().authenticated()`
as *anonymous* and yields **403, never 401**.

Every frontend caller has this shape:

```ts
if (response.status === 401) { onAuthExpired(); ... }
if (response.status === 403) { setMessage("The backend rejected this request (403)."); }
```

So after `security.jwt.expiration-ms` (1 hour) the user is still rendered as logged in —
`AccountMenu` shows their name, `App.tsx` still routes to `/ticks` because `currentUser !== null` —
while every load, create, edit, delete and import fails with "The backend rejected this request
(403)" forever. `onAuthExpired` is dead code. There is no refresh path. The user must manually
navigate to `/login`.

That a 403 branch already exists in all four components suggests someone hit this and papered over
the symptom rather than the cause.

**Fix:** add an `authenticationEntryPoint` returning 401, and have the filter distinguish
"no token" from "bad token". Then pin it with a test (see H3).

> **RESOLVED 2026-07-27 (`433c5b2`).** `SecurityConfig` now ends with an `.exceptionHandling(...)`
> block whose `authenticationEntryPoint` sets `WWW-Authenticate: Bearer` and then calls
> `sendError(401)`. Header before `sendError` matters — `sendError` commits the response, and
> anything set afterwards is silently dropped.
>
> No frontend change was needed. All five authenticated `fetch` call sites already branched on 401,
> and `onAuthExpired` → `handleLogout` → `setCurrentUser(null)` makes the route guard at
> `App.tsx:45` redirect on its own. The machinery was correct throughout; it had simply never
> received the signal. `/users` also stays correct: anonymous callers now get 401 via the entry
> point, authenticated ones still get 403 via the default `AccessDeniedHandler`.
>
> The filter still does **not** distinguish "no token" from "bad token". Both are correctly 401, so
> this is a messaging gap only — carrying `error="invalid_token"` through would let the UI say
> "your session expired" instead of a generic prompt.
>
> Still open downstream: the redirect is **silent** (no message, in-flight edits lost) — roadmap
> Phase 0.4 — and **M9**, which was masking this bug and is now safe to fix.

## High

### H1 — `tick.gradeValue` silently mixes two incompatible numeric scales

`GradeMappingService.java:45-47` stores `mapping.getSystemOrder()` when a mapping resolves and falls
back to `parsedGrade.gradeValue()` when it doesn't. **These are different scales.** Comparing every
seed row's `systemOrder` against what `GradeParser` computes for the same string: **67 rows disagree.**

| grade | seed `systemOrder` | parser value |
|---|---|---|
| `5.10` | 10.375 | 10.0 |
| `5.8-` | 7.7 | 8.0 |
| `4B` (Font) | 4.0 | 4.333 |
| `5C+` (Font) | 5.583 | 5.833 |
| `AI3` | 2.6 | 3.0 |
| `A6` | 5.25 | 6.0 |

The divergence is deliberate in the seed (sub-6A Font letters are *synonyms* folded onto numeric
rungs; `AI n` sits 0.4 below `WI n`), but `GradeParser` does naive letter-thirds arithmetic and
treats `WI`/`AI`/`M`/`A`/`C` identically. Two ticks both graded Font `4B` — one mapped, one not —
sort 0.33 grades apart in the same column. This directly undermines the leaderboard/comparison
feature the subsystem exists to enable.

**Fix:** the fallback should be `null`, not a value on a foreign scale. Nothing in the suite asserts
`getGradeValue()` at all, which is why this is invisible.

### H2 — Gym ticks in ICE / MIXED / AID / E_Grade can never resolve a mapping

`GradeMappingService.java:77-79` short-circuits: any tick with `discipline == GYM` looks up
discipline `GYM` regardless of system. But the CSV only has GYM rows for `YDS`, `FRENCH_SPORT`,
`FONT`, `V_SCALE` (78/84/73/72 rows respectively; **zero** for the other four).

A gym dry-tooling tick (`discipline=GYM`, `grade="M5"`) parses as `MIXED_M`, looks up
`(MIXED_M, GYM, "M5")`, finds nothing, and silently gets a null `difficultyScore` plus a
foreign-scale `gradeValue` per H1. `GradeSeedCoverageIntegrationTest` can't catch it — its
enumeration only pairs `GYM` with the four systems that do have rows.

### H3 — The auth tests are written to pass under either behaviour, which is what hid C2

`TickOwnershipIntegrationTest.java:192,229`

```java
mockMvc.perform(get("/ticks")).andExpect(status().is4xxClientError());
```

`is4xxClientError()` is satisfied by both 401 and 403. The one test that could have pinned the
contract the frontend depends on deliberately doesn't. Fixing C2 and later regressing it would both
stay green. Same for `importRequiresAuthentication`.

> **RESOLVED 2026-07-27 (`433c5b2`).** Both assertions tightened to `status().isUnauthorized()`, and
> a third test added — `expiredTokenIsUnauthorized` — which covers the path the other two never did.
> "No token" and "expired token" are different routes through `JwtAuthenticationFilter`; the
> existing pair only exercised the first.
>
> The expired token is minted in-test by constructing a `JwtService` with the running signing secret
> and a **negative** lifetime, so it is already expired at creation. No sleeping, no second Spring
> context, no `@TestPropertySource`.
>
> Caveat: these three were written after C2 was already fixed, so unlike the C1 test they have never
> been observed failing. Comment out the `.exceptionHandling(...)` block to confirm all three go red.
>
> The general lesson generalises past this finding: an assertion is only worth the wrong behaviours
> it rejects. `is4xxClientError()` rejects almost nothing. The same disease shows up in
> `createTickIgnoresBodySuppliedOwner`, which guards the `user` field correctly while the field that
> actually carried C1 — `id` — went unchecked. Right threat model, wrong specific.

### H4 — Editing a grade without also changing the system dropdown corrupts the mapping

`TickController.java:65` copies the client's `gradeSystem`, and `GradeMappingService.resolveGradeSystem`
(`:69-70`) treats any non-`UNKNOWN` requested value as authoritative. The edit form carries the old
`gradeSystem` forward (`TickCard.tsx:242`).

So editing a grade from `5.11a` to `V4` without touching the dropdown leaves `gradeSystem=YDS` on a
V-scale grade: the mapping lookup fails and `gradeValue` falls back to the YDS parse of "V4" (null).
`TickUpdateProvenanceIntegrationTest` only covers same-system edits.

## Medium

- **M1 — Import is non-transactional, non-idempotent, and its errors are unreadable.**
  `Importer.importCSV` has no `@Transactional` and saves row-by-row, so a malformed cell on row 500
  throws after rows 1–499 have committed. Retrying then duplicates them: `externalId` is never
  populated even though the MP `URL` column carries the route id, and there's no dedupe query.
  Meanwhile `ImportController` puts the message in a `ResponseStatusException` reason, but
  `server.error.include-message` defaults to `never` and `UploadPage` doesn't read the body anyway —
  the user just sees `Could not import CSV (400)`. `skippedRows` is incremented nowhere, so the UI
  always says "Skipped 0", and `ImportBatch` is written by no code path.

- **M2 — `GET /ticks` serializes the full nested `User` on every tick.** `Tick.user` has no
  `@JsonIgnore` (contrast `gradeMapping`, which has one), so every response echoes the owner's email
  and full name. It's the caller's own data today, so this is self-disclosure rather than a leak —
  but it becomes a real leak the moment any shared or cross-user view ships, which is Phase 5.3.

- **M3 — The seeder is upsert-only, non-transactional, and resurrects deactivated rows.**
  `GradeMappingSeeder.java:53` unconditionally re-asserts `setActive(true)` every boot, so a manual
  deactivation is undone on restart, and a row dropped from a regenerated CSV is never deactivated —
  it keeps serving the old score. 817 individual `findBy` selects with no `@Transactional` means a
  mid-batch failure leaves a partially retuned table. One malformed row bricks startup. There is no
  seeder test of any kind.

- **M4 — Entities are still bound directly as request bodies, with no `@Valid` anywhere.** This is
  the root cause of C1, and of registration 500ing on a missing password or duplicate email
  (`UserController.java:60-64` — no `@Valid`, no try/catch, no `@RestControllerAdvice` in the
  codebase). Constraint violations surface as 500s rather than 400/409.

- **M5 — The generator's coverage check validates strings, not the Java lookup path.**
  `docs/gen_grade_mappings.py:757-778` tests whether an MP `Rating` string appears in
  `known_raw_grades`, ignoring `gradeSystem`, `discipline`, case, and the Java normalizer. It
  therefore prints green for ~150 rows `GradeParser` can never classify (`6A/6A+`, `6A/+`, numeric
  Font `4+`, plain French `1`/`3+`, `WI3-4`, `AI2-3`, `M5-6`, bare `E5`, `E1/2`, `HVS`, `3rd`,
  `Easy 5th`). The seed data itself is clean — monotonicity and duplicate-key checks pass with zero
  violations.

- **M6 — Parser drops the modifier on letterless YDS.** `GradeParser.java:179-181` discards `-` and
  honours only `+`, so `5.8-` and `5.8` both return `8.0` while the seed has them at 7.7 and 8.0.
  The `5.9-` / `5.8+` pair inverts relative to the seed.

- **M7 — `RegisterForm.tsx` posts a field the backend has no concept of.** It sends
  `{username, email, password}`; `User` has `firstName`/`lastName` and no `username`. It also sends
  an `Authorization` header to a `permitAll` endpoint. Currently unreferenced (`RegisterPage` has
  its own correct inline form), so it's a landmine rather than a live break.

- **M8 — Six persisted fields remain invisible in the UI.** `pitches`, `stars`, `userStars`,
  `personalGrade`, `climbHeight`, `rawGrade` are populated by the importer and appear in neither
  `TickPayload`, `TickFormValues`, nor `TickCard`'s details — including the "Show Details" modal
  that claims to be the complete view. They now survive edits (per `a23a40d`) but are write-only
  from the user's perspective.

- **M9 — Session is memory-only.** `App.tsx:12` holds `currentUser` in `useState` with no
  persistence and there's no `/me` endpoint, so any refresh silently logs the user out while the JWT
  is still valid. This partially *masks* C2: users who habitually refresh re-login before expiry.

## High

### N1 — Adding an enum constant is a schema change, and nothing in the pipeline knows it

`V1__baseline.sql:64-65,96,146-150`; `Tick.java:32-74`; `application.properties:7`;
`application-test.properties` (`create-drop`, Flyway off); `Importer.java:67-81`.

Hibernate 6.2+/7 emits `CHECK (col IN (...))` for every `@Enumerated(EnumType.STRING)` column, and
the pg_dump baseline froze eight of them: five on `tick` (`discipline`, `grade_system`,
`rope_style`, `source_app`, `tick_type`), two on `grade_mapping`, one on `import_batch`. Two facts
turn that into a trap:

- `ddl-auto=validate` checks that tables, columns and types exist. It does not look at check
  constraints. The app boots clean.
- Tests run H2 `create-drop`, which regenerates the constraints from the *current* Java enum on
  every run. The suite cannot disagree with the enum, by construction.

So adding a constant — `RopeStyle.TOPROPE`, `TickType.FLASH`, `SourceApp.OPENBETA`, or whatever
Kaya (Phase 2) and 8a (Phase 4) need — passes `mvnw test`, passes the E2E job (N3 guarantees it),
boots in prod, and the first row written with the new value throws `DataIntegrityViolationException`
→ 500 on create/edit. Inside the importer it is worse: `tickRepository.save(tick)` at
`Importer.java:81` sits *outside* the per-row try/catch (`:67-77`), so one Kaya row with a new
rope style 500s the whole upload after earlier rows have committed, and the `ImportBatch` saved at
`:59-60` is left claiming `successfulRows = 0` while N ticks point at it.

CLAUDE.md's rule ("every schema change = a new numbered migration") is right, but nobody reads
"add an enum constant" as a schema change — and Hibernate `update` (which CI runs, N3) never alters
an existing constraint either, so it wouldn't have caught it in the pre-Flyway era.

**Fix** (pick one; do it before Phase 2 adds its first value):

1. Drop the eight check constraints in a V3 and let Java own the enum contract, as it already does
   for `tickConfig.ts`. Flyway owns prod DDL, so Hibernate never re-adds them there; the H2 test
   schema keeps generating them, harmlessly in sync. The trade — Postgres no longer rejects a
   hand-typed bad value — is one this project can afford.
2. Or keep them and make drift visible without Postgres: a plain JUnit test that reads
   `db/migration/V*.sql`, takes the latest definition of each `*_check`, and asserts
   `Enum.values()` ⊆ the listed literals. Then every enum change is *forced* to ship its
   `ALTER TABLE … DROP CONSTRAINT …; ADD CONSTRAINT … CHECK (…)`.

Either way, add "enum constants" explicitly to the CLAUDE.md schema-change rule.

### N2 — API routes share the SPA's URL space; only the dev proxy's Accept-header hack keeps them apart

`vite.config.ts:6-17,29-36`; `App.tsx:85-107`; `SecurityConfig.java:36`; `TickController.java:29`;
`UserController.java:37,64`; `playwright.yml:125-143`.

`/login`, `/register` and `/ticks` are simultaneously React routes and backend endpoints. In dev
that works because `apiProxy().bypass` sends any `GET` whose `Accept` includes `text/html` to
`index.html` and everything else to `:8080`. Nothing outside the Vite dev server provides,
documents, or tests that behaviour:

- A production reverse proxy routes by prefix — that is what nginx/Caddy do out of the box. With
  `location /ticks → backend`, a browser refresh on `/ticks` renders the API's `401` JSON, and a
  bookmarked `/login` gets `401` (only `POST /login` is permitted). Reproducing the Accept-header
  trick means a `map $http_accept` block someone has to know to write.
- Every new endpoint must be hand-added to the proxy list at `:29-36`. Miss one and the dev server
  answers with `index.html`; `response.json()` fails with `Unexpected token '<'` and the backend
  looks broken when it's a config omission.
- The E2E job runs against `npm run dev`, so no production topology is ever exercised.
- `VITE_API_TARGET` (`vite.config.ts:6`, documented in CLAUDE.md) exists to point the *dev* proxy
  at a remote backend. If that is how the VPS is being served — the June `vps-hotfix` commits are
  consistent with it — stop before anyone else uses it: `vite dev` is not a production server
  (unbundled sources, HMR socket, no caching), and its file-serving surface had a run of
  `server.fs.deny` bypass CVEs in 2025 that only matter when it is exposed on a network. Serve
  `dist/` from nginx/Caddy.

**Fix:** put the API under one prefix. `server.servlet.context-path=/api` is a one-liner —
security matchers and `/error` are context-relative so `SecurityConfig` doesn't move, the fetches
become `/api/...`, the Playwright `url().includes('/register')` checks still match, and the proxy
list collapses to `'/api'`. Any proxy is then `location /api/ → backend; location / → try_files
$uri /index.html`. Delete the `bypass` hack. Run the E2E suite (or at least a curl smoke) once per
push against `vite preview` behind that same rule so the prod shape is tested at all.

### N3 — CI's only Postgres job runs `ddl-auto=update`, so a missing migration can never fail CI

`.github/workflows/playwright.yml:65,99`; `application.properties:7`; CLAUDE.md ("migration bugs
remain invisible to the suite until we adopt Testcontainers").

The E2E job boots the real backend against a Postgres 16 service — Flyway on, `validate` in the
properties — and then sets `SPRING_JPA_HIBERNATE_DDL_AUTO: update`, a leftover from before Flyway.
Order of operations: Flyway applies V1/V2, then Hibernate `update` quietly adds whatever tables and
columns the entities have that the migrations don't. So the one job that could catch "entity
changed, migration forgotten" is configured to *repair* it. Live example: the working-tree
`SkippedRow` entity has no migration; on this branch that job goes green (Hibernate creates
`skipped_row`), while `spring-boot:run` against a Flyway-managed database fails at boot with
`Schema-validation: missing table [skipped_row]`. That is the production failure mode exactly:
green CI, app refuses to start.

**Fix:** delete line 99. The job then *is* the Postgres + Flyway + `validate` check the CLAUDE.md
caveat says doesn't exist yet — no Testcontainers required. Pin the service image to whatever prod
runs (dev was dumped from 17.10, CI uses 16). Entities and V1+V2 agree on `main` as far as reading
them goes, so it should pass; if it doesn't, that's a real drift and the finding earned its keep.

### N4 — `spring.servlet.multipart.max-file-size` defaults to 1 MB; real Mountain Project exports are bigger

`ImportController.java:26-33`; `UploadPage.tsx:56-80`; Boot 4.1.0 metadata (`max-file-size=1MB`,
`max-request-size=10MB`, `server.tomcat.max-swallow-size=2MB`); roadmap Part 1 #16.

Nothing in `application.properties` touches multipart, so the 1 MB per-file default applies.
`inputs/ticks.csv` is 802 rows in 180 KB ≈ 225 bytes/row, so the cap lands near **4,500 ticks** —
well inside a long-time MP user's export, and rows with real `Notes` are far longer than 225 bytes.
Two failure modes, neither naming the cause:

- File between 1 MB and roughly 3 MB: Tomcat rejects the part, Spring's
  `MaxUploadSizeExceededException` (an `ErrorResponse`, so `413`) reaches the client with an empty
  body; `UploadPage.tsx:68` shows "Could not import CSV (413)".
- Larger: Tomcat stops swallowing the remaining body after `max-swallow-size` (2 MB) and closes the
  connection; the browser sees a reset; `UploadPage.tsx:80` shows "Could not reach the backend."

Roadmap #16 records this as "no multipart size limits". The opposite is true: there is a limit and
it is too small. (Independent of the proxy's own cap — nginx also defaults to
`client_max_body_size 1m` — so there are two 1 MB walls to raise.)

**Fix:** set `spring.servlet.multipart.max-file-size` / `max-request-size` (20–25 MB comfortably
covers any personal logbook), raise `server.tomcat.max-swallow-size` to match (or `-1`), and the
proxy's body limit; handle `MaxUploadSizeExceededException` in `ApiExceptionHandler` with a message
that states the limit; check `file.size` client-side so the common case never leaves the browser.

## Medium

### N5 — No index on any foreign key, and ownership columns are nullable

`V1__baseline.sql:221-237`; `V2__importbatch.sql:1-6`; `TickRepository.java:8`;
`ImportBatchRepository.java:8`.

Postgres does not index FK columns automatically and neither the pg_dump baseline nor V2 adds any:
`tick.user_id`, `tick.grade_mapping_id`, `tick.import_batch_id`, `import_batch.user_id` are all
unindexed. `GET /ticks` (`findByUser`) is therefore a sequential scan of the *entire* `tick` table
on every request for every user — it degrades with total ticks, not the caller's, so the first few
imported users make everyone's list slower. (`findByIdAndUser` is fine — it hits the primary key.)
The same scan runs on every FK check when a `grade_mapping`, `import_batch` or user row is ever
deleted. Separately, `tick.user_id` and `import_batch.user_id` are nullable: ownership is enforced
in `TickController`, not the schema, so a null-owner row is a permanently invisible orphan.

**Fix:** V3: `CREATE INDEX` on all four columns; `ALTER TABLE tick ALTER COLUMN user_id SET NOT
NULL` (+ `optional = false` on the entity). Flyway runs each migration in a transaction so
`CREATE INDEX CONCURRENTLY` is unavailable — the plain form is instant at today's size, which is
exactly the argument for doing it now.

### N6 — Every timestamp is zone-less, and it only works because dev's server and browser share a timezone

`Tick.java:88-92`; `ImportBatch.java:33-34`; `V1__baseline.sql` (`created_at`, `updated_at`,
`imported_at` are `timestamp(6) without time zone`); `TickResponse.java:32-33`;
`TickCard.tsx:263-269`.

`@CreationTimestamp`/`@UpdateTimestamp` on `LocalDateTime` write the JVM default-zone wall clock
into a column with no zone. `TickResponse` serialises it as `2026-08-15T22:00:00.123456` (no
offset), and `formatDateTime` does `new Date(value)`, which the ECMAScript spec defines as *local
time* for offset-less date-time strings. On the laptop both ends are `America/Denver` and it
round-trips. On a VPS or container (UTC by default): a tick logged at 16:00 MDT is stored as
`22:00`, shipped as `22:00`, rendered "10:00 PM" — six hours off in "Created"/"Updated" and in any
future sends-by-hour or days-out stat. Worse: rows already written on the laptop are in Denver
time, rows written after deployment will be UTC, and the column can't tell them apart, so a later
fix has to guess per row.

**Fix (before the first prod row):** entity fields → `Instant`; columns → `timestamptz`
(`ALTER TABLE tick ALTER COLUMN created_at TYPE timestamptz USING created_at AT TIME ZONE
'America/Denver'` — the `USING` clause is where you declare what existing rows meant, and it's a
different answer for rows written after a UTC deploy, which is why *now*); JSON then carries `Z`
and `new Date()` is right everywhere. Set the JVM zone explicitly (`TZ=UTC`) so nothing depends on
the host. `tickDate` is a `LocalDate` and is correct as-is; `TickRecord.createdAt: string` and the
Playwright type-pin don't change.

### N7 — A deploy logs everybody out

`App.tsx:25-31,47-51`.

The session bootstrap treats any non-2xx from `/current_user` as "the server saw the token and
rejected it" and calls `handleAuthExpired()`, which deletes the token from `localStorage`. But
`!response.ok` is also: 502/503 from the proxy while the backend restarts (Boot 4's default
graceful shutdown drains the old process; the new one spends several seconds in Flyway + the
seeder before it listens); 500 when the database is briefly unreachable
(`JwtAuthenticationFilter` hits `userRepository.findByEmail` on every request); 429 once N8 adds
rate limiting. Any user who loads the app in that window is logged out and told their session
expired. The `.catch` branch already gets this right for transport failures; the `!ok` branch
doesn't.

**Fix:** clear the token on 401 only (403 arguably); on 5xx keep it, show "server unavailable", and
retry with backoff. The per-page 401 handlers are already correct.

### N8 — Nothing throttles `/login` or `/register`

`SecurityConfig.java:36`; `UserController.java:37-81`; `pom.xml` (no rate limiter, no filter).

Both endpoints are `permitAll`, unthrottled and unlimited. On a public host that means credential
stuffing against every registered email at line speed; a CPU-exhaustion vector — bcrypt at the
default cost is ~50–100 ms per `POST /login` with a valid email, by design, and nothing caps how
many the box will do concurrently; and unlimited free-form account creation with no verification,
so anyone can register *your* address and lock you out of ever registering it. None of it is
visible until the app has an address someone else can reach.

**Fix:** cheapest durable answer is at the proxy — nginx `limit_req` on `/login` and `/register`
per IP (single-digit r/s, small burst); in-app alternative is a Bucket4j-style filter keyed by
IP + email. Add a per-account progressive delay after N failures. Decide whether registration
stays open before public exposure; if it does, email verification is a prerequisite for the
Phase 5 privacy model anyway.

### N9 — Passwords over 72 bytes 500 on both register and login

`UserController.java:46-49,77`; `RegisterRequest.java:17`; `LoginRequest.java` (no validation);
Spring Security 7.1.0 `BCrypt` (`"password cannot be more than 72 bytes"` — verified in the jar).

`RegisterRequest` says `@Size(min = 8)` and nothing else. Spring Security's
`BCryptPasswordEncoder` no longer truncates silently: it throws `IllegalArgumentException` when the
UTF-8 encoding exceeds 72 bytes — a passphrase user, a password manager set to 100 characters, or
25 emoji. `encode` at `:77` and `matches` at `:46` both take that path, and nothing catches it —
`ApiExceptionHandler` handles only `MethodArgumentNotValidException`. Result: 500 on register, and
on login **500 for a known email vs 401 for an unknown one** (a third enumeration channel, see N17).
`LoginRequest` also has no `@Valid`/`@NotBlank`: a body without `password` reaches
`matches(null, …)` and 500s the same way. (`LoginRequest` also carries two dead fields and a
constructor that assigns backwards — replace it with a record like `RegisterRequest`.)

**Fix:** validate the *byte* length on `RegisterRequest` (a custom constraint — `@Size` counts
UTF-16 units, and 72 CJK/emoji chars is > 72 bytes) and give `LoginRequest` the same guard; catch
`IllegalArgumentException` in login and return 401. Add a catch-all `@ExceptionHandler(Exception)`
→ 500 with a request id, so unexpected exceptions neither leak nor vanish.

### N10 — Email is case-sensitive and un-normalised end to end

`User.java:24-25`; `UserRepository.java:6`; `UserController.java:40,68`; `JwtService.java:34,52`;
`V1__baseline.sql:205`.

`findByEmail` is an exact match, the unique constraint is on the raw column, and the JWT subject is
the raw string. So `Riley@Example.com` and `riley@example.com` are two accounts; a user who
registers with a capital and later types lowercase gets "Invalid email or password"; and the
deliberate 409 oracle (`:66-67`) is bypassed by changing case. The trap is the fix: the day this is
corrected with a `lower(email)` unique index or `citext`, the migration fails if any two rows
collide — a manual merge of two users' ticks. Zero rows collide today.

**Fix now:** `trim().toLowerCase(Locale.ROOT)` at register and login; V3:
`CREATE UNIQUE INDEX ON app_users (lower(email))` plus one `UPDATE … SET email = lower(email)`.
(The RFC says the local part may be case-sensitive; every provider folds it and every auth system
does this.)

### N11 — PUT lets the client rewrite provenance, which quietly defeats the planned idempotency key

`TickController.java:88-90`; `TickRequest.java:20-24`; `TickCard.tsx:243-246`; roadmap Phase 1.4.

`applyRequest` copies `sourceApp`, `externalId` and `sourceUrl` from the body on every update, and
the edit form round-trips them as editable inputs. Roadmap 1.4 plans dedupe on
`(user, sourceApp, externalId)` with a unique constraint. Once that lands: blank `externalId` on an
imported tick (or flip `sourceApp` to `MANUAL`) and the next re-import duplicates it; set two ticks
to the same `externalId` and either the constraint migration fails on existing data or the PUT
500s with a constraint violation. `TickUpdateProvenanceIntegrationTest` pins `rawGrade` and
`climbHeight` survival; nothing pins these three.

**Fix:** treat `sourceApp`/`externalId`/`sourceUrl`/`importBatch` as server-owned after creation —
ignore them on update (or split a `TickUpdateRequest` without them), render them read-only in the
form, and add the test. Before 1.4, not after.

### N12 — Import throughput and timeouts at VPS latency (M1's other half)

`Importer.java:59-88`; `application.properties` (no `spring.jpa.open-in-view` → default `true`);
`Tick.java:24-26`, `ImportBatch.java:19-21` (`IDENTITY`); Hikari default pool 10.

M1 covers atomicity. The deployment-shaped consequences are separate. Every row is its own
transaction (`save` autocommits — no outer `@Transactional`), preceded by a `grade_mapping` lookup,
and with `IDENTITY` ids Hibernate cannot JDBC-batch inserts at all. On the laptop those are
sub-millisecond round-trips; on a VPS talking to a remote or managed Postgres it's a few ms × ~3
statements × N rows — a 5,000-row export walks into nginx's default 60 s `proxy_read_timeout`. The
proxy returns 504, the user sees "Could not import CSV (504)", the server *keeps importing* (the
request thread doesn't know), and the natural response — retry — doubles the ticks (idempotency is
1.4, not shipped). Meanwhile OSIV pins a pool connection to the request for its whole life; ten
slow imports (or one slow import and nine slow anything) exhaust the pool of 10 and every other
request waits. Boot 4's default graceful shutdown (30 s phase timeout) also cuts a long import in
half on every deploy — mid-batch, non-idempotent.

**Fix:** `@Transactional` on `importCSV` (M1) plus `spring.jpa.open-in-view=false` (Boot logs a
warning about it at every boot for a reason); `SEQUENCE` ids with an allocation size and
`hibernate.jdbc.batch_size` — imports become a couple of round-trips per 50 rows; longer term,
accept the file, return the batch id, run the import off-thread with a status endpoint
(`ImportBatch` already has the shape). Land 1.4 idempotency before opening imports to anyone else,
precisely because retries will happen.

### N13 — No health/readiness endpoint, and the port opens before the app is ready

`pom.xml` (no actuator); `GradeMappingSeeder.java:16-25` (`ApplicationRunner`);
`playwright.yml:104-115` (TCP-port readiness check).

There is nothing for systemd, Docker, a load balancer or an uptime monitor to probe except "does
:8080 accept TCP" — which is also what CI does. But Tomcat starts listening at context refresh,
*before* `ApplicationRunner`s execute, so during the seeder's pass the app serves requests against
a partial `grade_mapping` table (a tick created in that window gets `difficultyScore = null` — the
"stranded" case `grade-mapping-review.md` describes), and if the seeder throws (the concurrent-boot
race documented there) the process exits *after* having answered traffic. Port-open ≠ ready.

**Fix:** `spring-boot-starter-actuator`, expose only `health` (permitAll it in `SecurityConfig`),
enable the liveness/readiness groups, and have the proxy/orchestrator — and CI's wait loop — gate
on `/actuator/health/readiness`.

## Low

- **N14 — Flyway baseline knobs left permanently on.** `application.properties:13-14`.
  `baseline-on-migrate=true, baseline-version=1` was right once, for the one pre-Flyway dev
  database. Left on, any non-empty schema the app is ever pointed at is silently stamped "at V1"
  and V1 skipped — a database where someone pre-created a table or extension then fails at V2 with
  `relation "tick" does not exist`, and the error reads as a broken migration rather than a wrong
  flag. Turn it off now that every environment is baselined. Two related notes: the baseline is a
  raw pg_dump whose `SET`/`search_path` preamble and hard-coded `public.` schema assume the app's
  DB role can create in `public` (Postgres 15+ revokes that from non-owners by default — make the
  app user own the database); and it froze Hibernate's opaque constraint names
  (`fkilvbmhxevn0m1q4rq2we1bemv`, `uk4vj92ux8a2eehds1mdvmks473`) as the names every future
  migration must reference.

- **N15 — Two additions to the V4 string-length audit, plus a WIP design note.** `ImportBatch.java:29` /
  `V1__baseline.sql:91`: `original_filename` is client-controlled (`file.getOriginalFilename()`,
  `ImportController.java:33`) and capped at 255 — a long filename rejects the batch *before* any
  row is read. On the working-tree `SkippedRow`: `reason` holds exception messages (commons-csv's
  "Mapping for X not found, expected one of [15 headers]" is already ~200 chars) at the default
  255 — CLAUDE.md's own rule says error messages are TEXT; and `@Id private long recordNumber`
  (`SkippedRow.java:11-12`) is per-file, not global — the second batch that skips row 2 collides
  on the primary key. Give it a generated id (or a composite with `importBatch`) before V3 is
  written; the migration is much cheaper than the fix after.

- **N16 — Token storage and the XSS blast radius.** `App.tsx:14,17,45`; `TickCard.tsx:135`. M9
  moved the JWT to `localStorage` — right call for the refresh problem — which turns roadmap #25
  (`javascript:` in `sourceUrl`, rendered as a raw `href`) from "runs script" into "exfiltrates a
  bearer token that stays valid for an hour with no server-side revocation" — a future
  password-change feature won't kill it either (`JwtService` has no `jti`/version to check). Two
  cheap mitigations that fit the client-agnostic API goal: fix #25 (scheme allow-list on
  `sourceUrl` at write *and* render time) and ship a `Content-Security-Policy` with the SPA. Add a
  token-version claim checked in the filter when account management lands.

- **N17 — Login is a timing oracle for the same fact the 409 leaks.** `UserController.java:40-53`.
  Unknown email returns 401 in microseconds; a known email pays bcrypt first (and per N9, 500 vs
  401 for long passwords). The 409 on register is documented as accepted-for-now; when it's
  revisited (Phase 5), close both at once — run `matches` against a fixed dummy hash on the
  unknown-email path.

- **N18 — No optimistic locking on `Tick`.** `Tick.java` (no `@Version`). Two tabs, or the web app
  and the planned iOS client, editing the same tick: last write wins with no signal, and the edit
  form is populated from a list fetched at page load, so "stale" is the normal case. A
  `version bigint not null default 0` column is a one-line migration now and a data audit later;
  the API can then 409 on conflict, which the DTO layer already knows how to surface.

- **N19 — Logs will contain climb notes.** `Importer.java:75` logs each skipped row's full content
  (`Raw row: {…}` — including `Notes`, i.e. whatever the user wrote about their day) at WARN, and
  `spring.jpa.show-sql=true` (roadmap hygiene) prints every statement to stdout. Neither matters
  on a laptop; on a shared host with journald/log shipping it's other people's prose in your logs
  with no retention policy. Log the record number and reason; keep the raw row in the response (or
  the `SkippedRow` table) where only its owner can see it.

- **N20 — AGENTS.md is stale in the two places an agent would act on.** `AGENTS.md:12` still says
  this review has "two open criticals" (fixed 2026-07-27), and `:114` says production runs
  `ddl-auto=update` (it has run `validate` under Flyway since 2026-08-08). CLAUDE.md is current;
  agents that read AGENTS.md first will plan around wrong facts.

## Deployment checklist

Not code defects — decisions nobody has written down yet, collected here so they don't get made by
default: TLS terminates at the proxy, so set `server.forward-headers-strategy=framework` (Boot
default is `None`; without it Spring believes every request is `http` and Spring Security never
sends HSTS); `JWT_SECRET` and DB credentials via env/secret store, never on a command line (`ps`
shows it); the app's DB role owns the database (N14); backups plus a *tested* restore before the
first non-owner account; log rotation/retention (N19); `TZ=UTC` on the host (N6); proxy
`client_max_body_size` (N4) and `proxy_read_timeout` (N12); readiness gate (N13); rate limits (N8).
