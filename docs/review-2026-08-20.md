# TickList — Code Review, 2026-08-20

Scope: the most recent work on `main` — PR #21 (`99c7bfe` "import overhaul" + `52edb81` "migration
with import batch added"), merged as `5556189`. That is the newest code in the repo; nothing has
landed since 2026-08-15.

Diff reviewed: `git diff 32d8ba3 5556189` — 11 files, +150/-8. Backend suite run at `5556189`:
**passing, exit 0.**

**Headline:** the change itself is sound — `ImportBatch` is the right seam, the entity/DTO boundary
held (`TickResponse` correctly did *not* grow an `importBatch` field), and the migration is valid
against the V1 baseline. The problems are all in what the change *didn't* do: the import path is
still non-transactional, the new association is eager and unindexed, and the app's headline feature
still has no integration test.

## Immediate

### I1 — Uploads over 1 MB fail with an unhandled 500

`spring.servlet.multipart.max-file-size` is never set. Verified against the Spring Boot 4.1.0
metadata (`spring-boot-servlet-4.1.0.jar!/META-INF/spring-configuration-metadata.json`):

    spring.servlet.multipart.max-file-size  = '1MB'
    spring.servlet.multipart.max-request-size = '10MB'

`ApiExceptionHandler` handles only `MethodArgumentNotValidException`, so
`MaxUploadSizeExceededException` escapes as a 500. `UploadPage.tsx:69` then renders:

    Could not import CSV (500).

A Mountain Project export runs roughly 150–300 bytes/row bare, and over 1 KB/row once a climber
writes notes — so the cap lands somewhere between ~1,000 and ~7,000 ticks. That is squarely inside
the target user's range, and when they hit it they are told nothing actionable.

Fix: set the limit explicitly, and add a `MaxUploadSizeExceededException` handler returning 413 with
a message naming the limit.

### I2 — The import is not transactional; the batch counters can lie

`Importer.importCSV` (`Importer.java:59-87`) saves the batch, then saves N ticks, then updates the
batch counters — each in its own auto-commit transaction, since nothing on the path is
`@Transactional`.

Any failure once the loop has started (connection drop, a constraint violation on row 900) leaves
persisted ticks behind *and* a batch row still reading `successfulRows=0, failedRows=0`. The entire
point of `ImportBatch` is provenance; a provenance record that survives in a state contradicting the
data it describes is worse than none. The caller meanwhile sees a 500 with half the ticks committed
and no way to tell which half.

Fix: `@Transactional` on `importCSV` so the batch, the ticks, and the final counters are one unit of
work.

### I3 — `Tick.importBatch` is EAGER and loads on every tick read

`Tick.java:68` — `@ManyToOne` defaults to `FetchType.EAGER`. `Tick` now carries **three** eager
associations: `user` (L38), `gradeMapping` (L58), and now `importBatch` (L68).

`TickRepository.findByUser(user)` backs `GET /ticks`. `TickResponse` uses none of `importBatch`, so
every list request now pulls an import-batch row per tick for nothing.

Fix:

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "import_batch_id")
private ImportBatch importBatch;
```

### I4 — The new foreign key has no index

`V2__importbatch.sql` adds `tick.import_batch_id` and its FK constraint, but no index. Postgres does
not auto-index the child side of a foreign key: every `DELETE FROM import_batch` (i.e. the "undo
this import" feature this table exists to enable) sequentially scans `tick`, as would any
"what did this import bring in" query.

Worth stating plainly while we're here: **`V1__baseline.sql` contains zero non-unique indexes.**
`tick.user_id` is unindexed, and that is the hot path behind every single list request. The baseline
inherited whatever Hibernate generated; nobody has done an index pass yet.

### I5 — `originalFilename` is unvalidated user input into a `varchar(255)`

`ImportController.java:33` passes `file.getOriginalFilename()` straight through to the entity. V1
declares `original_filename character varying(255)`. A filename longer than that raises
`DataIntegrityViolationException` — unhandled, so another 500, and per **I2** it fires *after* the
ticks are already committed. Truncate or validate at the boundary. (`tick.climb_name` is the same
shape of exposure: `NOT NULL varchar(255)`, fed unchecked from the CSV.)

### I6 — Comment describes behaviour the code doesn't have

`Importer.java:57`:

```java
// Saved before the loop so ticks and skipped rows have an id to point at,
// and so a batch exists even when every row fails.
```

Skipped rows never get an id to point at. `SkippedRow` has no batch reference and is not persisted
at all — it lives only in the HTTP response and is gone the moment the page is closed. The second
half of the comment is true and is the real reason for the ordering. Either drop the first clause or
land the `import_skipped_row` table it's promising.

## Longer-term

### L1 — There is still no import idempotency, and the key for it is already parsed

Re-uploading the same CSV duplicates every tick. `Tick.externalId` exists as a field and the importer
**never sets it** — meanwhile `processMTNProjectRow` already reads the `URL` column into
`sourceUrl`, and the MP route id is right there inside it.

Pulling that id out gives a natural `(user, source_app, external_id)` unique key. That one change
unlocks dedupe, re-import-as-update, and the Kaya/8a.nu merge story that the whole importer
abstraction (PR #20) was built for. It is the highest-leverage item on this list.

### L2 — The import path has no integration test

`ImporterTest` mocks both `TickRepository` and `ImportBatchRepository`. There is no
`ImportControllerIntegrationTest`. So for the app's headline feature there is **zero** real-database
coverage of: the new FK, the batch row actually persisting, ownership on imported ticks, or the
multipart endpoint end-to-end.

Ticks and auth each have an integration test. Import — the thing the product is for — does not.

### L3 — The new assertions are weaker than they read

In both new blocks in `ImporterTest`, the captor captures the *same mutable instance* twice, because
the code mutates the batch in place rather than replacing it. So `batchCaptor.getValue()` and
`getAllValues().get(0)` are the same object, and the "saved before the loop" property the comment
calls out is proven only by `times(2)` — never by any state assertion.

Related: the code ignores `save()`'s return value, so the mock returning `null` is harmless *today*.
Switching to the idiomatic `batch = importBatchRepository.save(batch)` would NPE under this mock
while the production code got more correct. Small, but it's false confidence in exactly the
assertion the comment says matters.

### L4 — Migrations have now started accumulating and still never execute

Test profile is `ddl-auto=create-drop` with `spring.flyway.enabled=false`. That was a deliberate,
documented deferral at baseline time — but V2 is the first *real* migration on top of the baseline,
so the deferred cost is now live debt rather than a hypothetical. `V2__importbatch.sql` has never
been executed by CI.

Minimum viable fix short of Testcontainers: a CI job with a Postgres service that runs
`flyway:migrate` from empty and then boots the app with `ddl-auto=validate`. That catches both
migration syntax errors and entity/schema drift, which is most of the risk.

### L5 — `baseline-on-migrate=true` should come off now

`application.properties` still carries `spring.flyway.baseline-on-migrate=true`. It was needed once,
to adopt the existing schema. Left on, a future deploy against a database that has tables but no
`flyway_schema_history` will silently baseline at V1 and skip it — rather than failing loudly, which
is what you want. The baseline is taken; turn it off.

### L6 — `ImportBatch` entity hygiene

- Public `setId(Long)` and `setImportedAt(...)` — the latter on a `@CreationTimestamp` field. Both
  are traps, and this repo has already eaten one mass-assignment IDOR from entity binding at the
  boundary (C1 in the 2026-07 review). Drop them.
- No `nullable = false` on `user` or `sourceApp`; V1 permits NULL for both, so orphan batches are
  representable.
- `ImportBatchRepository.findByUser` / `findByIdAndUser` are dead code — nothing calls them, and no
  endpoint exposes batches yet. Fine as forward-looking scaffolding, but when the endpoint lands it
  needs an `ImportBatchResponse` DTO, not the entity.

### L7 — `spring.jpa.show-sql=true` in the base properties

Logs every statement in production. During a 3,000-row import that is 3,000+ lines of noise, plus
the throughput cost. It's correctly `false` in the test profile; move the `true` to a dev profile.

### L8 — Entity and migration should ship in one commit

`99c7bfe` added `Tick.importBatch`; `52edb81` added `V2__importbatch.sql` seven hours later. Both
landed in PR #21, so `main` was never broken — but `99c7bfe` on its own will not boot, because
`ddl-auto=validate` fails against a schema with no `import_batch_id`. That makes `git bisect` across
this range unreliable. Schema change and the migration that enables it belong in the same commit.

### L9 — Raw CSV rows, including private notes, go to logs and to the API response

`Importer.java:72` builds `rawRow` from `record.toMap().toString()` and puts it into both
`log.warn(...)` and the `SkippedRow` returned to the client. That row contains the climber's `Notes`
verbatim. Harmless for a single-user local app; a real problem the first time logs ship anywhere.
Worth deciding now, before there's a log aggregator.

## Suggested order

1. **I2** (`@Transactional`) and **I3** (`LAZY`) — two-line fixes, both correctness/performance wins.
2. **I1** + **I5** — one small pass over upload-boundary validation and `ApiExceptionHandler`.
3. **I4** — one migration adding indexes on `tick.import_batch_id` and `tick.user_id`.
4. **L2** — an import integration test, which then makes **L4** cheap to add.
5. **L1** — `externalId` and dedupe, before Kaya makes the merge problem twice as hard.
